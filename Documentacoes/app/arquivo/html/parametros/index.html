arrow_downward Definições

O Parâmetro é o mecanismo que permite a um caso de teste configurar o próprio sistema antes da execução. As units (P39_TDD_PARAMETRO e P39_TDD_PARAMETRO_MAPEAMENTO) leem o bloco parametros do JSON do caso de teste, escrevem o valor no banco de dados do ERP e reconectam a sessão para que o ERP carregue os novos valores em memória.

Sem esse mecanismo, um teste que depende de uma configuração específica (ex.: "faturar por unidade fabril") teria de deixar o sistema configurado manualmente antes de rodar, o que tornaria a suíte não repetível e dependente do ambiente.

O parâmetro do caso de teste é autoaplicado: não existe necessidade de executar um processamento separado. Ele é aplicado pela etapa STARTED do Runner, imediatamente após o carregamento do caso, e é cronometrado como etapa própria (AplicarParametrosDoCasoTeste).

A aplicação acontece em duas situações:

  • No STARTED (via AplicarParametrosDoCasoTeste) - aplica os parâmetros de todos os casos de teste carregados na área, uma vez, antes do IRUNNER executar;
  • Na troca de caso (via P39_TDD_FAT_DOCUMENTO_FATURA.SetCasoTeste) - o módulo de Faturamento fecha o formulário, reaplica os parâmetros e reabro a tela, porque a mudança de configuração invalida o formulário já aberto.

  • arrow_downwardTabelas do ERP Alteradas

    Os parâmetros são gravados diretamente nas tabelas de configuração do ERP (não no banco dedicado de testes). Sempre restrito à empresa atual (Codigo_Empresa_Atual). São três:

    Tabela Chave do filtro
    CONFIG_SISTEMA Configuração global (sem filtro por empresa no UPDATE)
    CONFIG_SISTEMA_EMPRESA EMPRESA_CFSEMP = Codigo_Empresa_Atual
    PCP_CONFIG CODIGO_CONFIG = Codigo_Empresa_Atual

    warning Os parâmetros são persistidos no banco e não são revertidos ao final da execução. Ao terminar a suíte, o ambiente fica com a última configuração aplicada. Em bases dedicadas de teste isso é aceitável, mas em ambientes compartilhados exige atenção.

arrow_forward Instruções de uso

arrow_downward Fluxo geral de uso

Para usar um parâmetro em um caso de teste:

  1. Verificar se a chave já está mapeada em P39_TDD_PARAMETRO_MAPEAMENTO; caso contrário, adicionar o mapeamento;
  2. Incluir a chave e o valor no bloco parametros do JSON do caso de teste;
  3. Publicar a unit P39_TDD_PARAMETRO_MAPEAMENTO na Tek-Store, se ela foi alterada;
  4. Executar o caso de teste. O STARTED aplica os parâmetros automaticamente.

Exemplo de bloco parametros:

"parametros": {
  "Fat_PorUnidadeFabril": true,
  "OrdemImpressaoItemNF": 0
}

arrow_downward Como a aplicação acontece

A rotina VerificarParametros(pJSONParametros) executa o seguinte para cada par chave/valor do objeto JSON:

  1. Filtra por necessidade de alteração - NecessarioModificarParam compara o valor informado com o valor atual (GetValueJson(SecaoParametroJson, pCampo)). Se forem iguais, o parâmetro é descartado e nenhum acesso ao banco é feito;
  2. Infere o tipo do valor a partir do próprio texto JSON, pela rotina PegarTipoCampo:
    • contém " → string
    • é true ou false → booleano
    • contém . → currency
    • caso contrário → inteiro
  3. Acumula apenas os parâmetros a alterar em um TClientDataSet (CHAVE, VALOR) indexado pela chave;
  4. Executa um UPDATE por parâmetro acumulado, na tabela correspondente ao mapeamento;
  5. Reconecta a sessão do ERP (rotina Relogar) para recarregar a seção atual com os novos valores.

Montagem do UPDATE

O valor é convertido conforme o tipo inferido, e o WHERE é montado conforme a tabela:

Tipo inferido Conversão aplicada
String Remove as aspas e envolve em QuotedStr
Inteiro / Currency Usado como está, sem aspas
Boolean true → 'S', false → 'N'

warning A execução do UPDATE é envolvida em try / except que engole a exceção. Uma falha ao gravar o parâmetro não interrompe a execução do teste — ela apenas não surte efeito, e o teste pode falhar mais adiante por isso. Em caso de falha (parâmetros), verificar o log do processamento e o estado real da tabela de configuração.

Rotina Relogar

Após aplicar os parâmetros, a rotina Relogar reabre o data module de conexão (DMCriadoPeloNome('DMConexao')) chamando ConectaServidorAplicacao e, em seguida, CarregaSecaoAtual. É esse passo que faz o ERP enxergar a nova configuração — sem ele, o banco teria o valor novo, mas a sessão continuaria com o valor antigo.

arrow_downward Carregamento inicial dos parâmetros

Na inicialização (Setup_Inicializar_Parametros, chamada por Setup_Inicializar_CasosTeste):

  1. MapearParametros monta o mapa de parâmetros (idempotente);
  2. É montado o SELECT que junta as três tabelas de configuração, usando o método CamposCadastro de cada classe (TClassConfigSistema, TClassConfigSistemaEmp, TClassPCP_Config) para montar a lista de colunas automaticamente;
  3. O resultado é carregado no CDSParametro e as propriedades dos campos são configuradas pelos mesmos métodos ConfigurarPropriedadesDosCampos.

O CDSParametro é a imagem atual dos parâmetros - é ele que permite o filtro por necessidade de alteração.

arrow_downward Reaplicação na troca de caso

O módulo de Faturamento executa todos os casos de teste da área. Como cada caso pode ter parâmetros diferentes, a rotina SetCasoTeste da unit P39_TDD_FAT_DOCUMENTO_FATURA reabastece o contexto do caso e, se houver parâmetros:

  1. fecha o formulário de pedido de venda (a configuração invalida o formulário aberto);
  2. chama {TDD_PARAMETRO}VerificarParametros;
  3. reabre o formulário via Setup_IniciarFormulario.

info Esse ciclo de fechar/reabrir executa uma vez por caso de teste na área. Em áreas com muitos casos, é a maior parcela de tempo da execução - e aparece isoladamente na métrica Total de METRICAS_TICK_DIFF.

arrow_forward Instalação e configurações

Necessário publicar na Tek-Store as units P39_TDD_PARAMETRO e P39_TDD_PARAMETRO_MAPEAMENTO. A unit de mapeamento é carregada como dependência da unit de parâmetros.

O usuário que executa a suíte precisa de permissão para alterar CONFIG_SISTEMA, CONFIG_SISTEMA_EMPRESA e PCP_CONFIG na base de dados do ERP em uso.

Ao mapear um novo parâmetro

Adicionar em MapearParametros, respeitando o próximo índice livre:

Add(9, 'NomeDoParametro', 'CAMPO_NO_BANCO', cTabelaConfigSistema);

A constante da tabela deve ser uma das três já declaradas: cTabelaConfigSistema, cTabelaConfigSistemaEmpresa ou ctabelaConfigPCP.

warning O limite do array de mapeamento é array [0..8]. Ao ultrapassar a 9 entradas, é necessário alterar o limite em FMapeamentoParam — do contrário o mapeamento é corrompido em memória.

Restrições

  • O filtro de empresa é aplicado somente a CONFIG_SISTEMA_EMPRESA e PCP_CONFIG. Em CONFIG_SISTEMA o UPDATE é executado sem WHERE, pois a tabela tem um único registro por parâmetro;
  • Chaves não mapeadas são ignoradas silenciosamente: o filtro NecessarioModificarParam já as descarta por não encontrarem o valor atual;
  • A comparação de valor atual depende de a chave existir na seção JSON do ERP (SecaoParametroJson) — chaves não publicadas na seção nunca são aplicadas.

arrow_forward Observações importantes

  • Sem rollback. Parâmetros aplicados permanecem no banco após a execução. Se a suíte precisar restaurar a configuração original, isso deve ser feito explicitamente (por exemplo, com um caso de teste final que reaplique os valores originais).
  • Escopo por empresa. Tudo é filtrado por Codigo_Empresa_Atual. A mesma suíte executada em filiais diferentes altera configurações diferentes — comportamento esperado e desejado.
  • Aplicação incremental. Só parâmetros cujo valor realmente mudou são gravados, o que reduz drasticamente a quantidade de UPDATE e de reconexões.
  • Falha silenciosa. Exceções de escrita são engolidas por desenho (ver alerta na seção de aplicação). O sintoma típico é o teste falhar por "comportamento não aplicado" e não por erro de configuração - sempre conferir o valor efetivo na tabela antes de suspeitar do código do teste.
  • Booleano por convenção do banco. Valores lógicos são persistidos como 'S' / 'N', enquanto o JSON usa true / false. A conversão é automática em AtualizarParametros, mas é comum errar o lado do JSON ao escrever novos casos.
  • Inferência de tipo por formato. O tipo não é declarado no JSON: é deduzido do texto do valor. Um número sem ponto decimal (ex.: 10) é tratado como inteiro; para um Currency é necessário informar o separador decimal (ex.: 10.5).
  • Mapeamento único carregado por sessão. A flag FParametroMapeado impede recarregar o mapa mais de uma vez. Alterações no mapa só têm efeito em nova sessão do ERP.
