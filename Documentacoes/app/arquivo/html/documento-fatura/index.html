arrow_downward Definições

As units DOCUMENTO_FATURA são o caso de uso mais completo da suíte de testes automatizados: implementam um pedido de venda virtual, inteiramente na tela real do ERP. O roteiro percorre o formulário de pedido de venda (o mesmo que o usuário utiliza), preenche os campos a partir do JSON do caso de teste, inclui itens e grava o documento.

O objetivo é não simular a funcionalidade: o teste aciona os mesmos componentes, eventos e DataSets da aplicação, de modo que qualquer regressão no cadastro de pedidos de venda é detectada como falha real do teste.

Este processamento é exclusivo para uso de testes dentro da TekSystem e não pode ser executado pelo servidor. A rotina Main da unit faz as duas validações e aborta com exceção caso contrário:

  • if ExecutandoNoServidor then raise exception...
  • if CodigoComoClienteTekSystem <> 1000 then raise exception...

Ao final da inclusão de cada documento, a unit monta uma observação automática no campo OBSERVACAO_DOCFAT contendo o texto "Documento gerado automaticamente via rotina de testes automatizados" e a descrição do caso de teste — o que permite rastrear, no próprio cadastro, a origem do documento.

  • arrow_downwardConfiguração do Módulo

    A unit P39_TDD_CASOS_DE_TESTE carrega, para o módulo FATURAMENTO, o registro único da tabela FATURAMENTO_CONFIGURACAO. Os campos mais relevantes para a geração de documentos são:

    Campo Uso no teste
    PESSOA_GERAL_FATCONFIG Cliente usado quando o caso de teste não informa tag_cliente nem cliente_docfat
    PEDIDO_VENDA_FATCONFIG Transação de venda padrão, sobrescrevendo a informada no JSON
    QTD_FIXA_ITEM_FATCONFIG Quantidade fixa do item (quando não informada no JSON)
    QTD_MAX_ITEM_FATCONFIG Limite superior para sorteio aleatório da quantidade
    VALOR_ITEM_FIXO_FATCONFIG Valor unitário fixo do item
    VLR_MAX_ITEM_FATCONFIG Limite superior para sorteio aleatório do valor unitário

    info Quando não há valor fixo configurado, quantidade e valor unitário são sorteados aleatoriamente (Random), com piso de 1 para quantidade e 10 para valor. Isso é útil para variar a massa de teste, mas exige que o resultado esperado use operadores tolerantes (Maior / Menor) em campos derivados (valor bruto, descontos, etc.).

arrow_forward Instruções de uso

arrow_downward Fluxo geral de uso

O roteiro de execução é:

  1. A unit de caso de teste (P39_TDD_FAT_PEDIDO_VENDA) é a entrada: ela define o formulário e o data module, e registra os métodos Setup e Teste para o IRUNNER executar;
  2. Setup chama Setup_Inicializar, que carrega os casos de teste do módulo Faturamento / área Pedido de Venda e abre o formulário de pedido de venda;
  3. Teste chama Teste_Executar, que percorre todos os casos de teste ativos carregados;
  4. Para cada caso: define o contexto JSON, inclui um documento por cliente encontrado e marca o caso como executado.
uses P39_TDD_FAT_DOCUMENTO_FATURA;

const cArea = 'PEDIDO DE VENDA';

procedure Setup;
begin
  FCadastro := 'FCadPedidoVenda';
  FDM       := 'DMCadPedidoVenda';
  SetArea(cArea);
  Setup_Inicializar;
end;

procedure Teste;
begin
  Teste_Executar;
end;

warning Teste_Executar percorre todos os casos de teste da área, não apenas um. Para executar um caso específico, filtre-o por DESCRICAO no CDSCasosTestes ou utilize a carga individual pela unit P39_TDD_CARREGAR_CASO_TESTE.

arrow_downward Montagem do documento

Para cada cliente encontrado, a rotina _IncluiDocumento executa a sequência de preenchimento e gravação: 

BotaoIncluirClick  (novo documento)
 ├─ _DadosPrincipais    (cliente, unidade fabril, tabela, desconto e itens)
 ├─ _Financeiro         (financeira e banco)
 ├─ _DadosParaEntrega   (datas, campanha, parceria, dias de entrega)
 ├─ _DadosFaturamento   (transação)
 └─ _InformacoesFrete   (frete manual / embutido e frete fiscal)
BotaoGravar.Click

A ordem importa: os itens são incluídos dentro de _DadosPrincipais, e o frete é processado por último porque depende dos valores calculados com os itens já lançados.

Seleção de clientes

A origem dos clientes segue uma ordem de prioridade:

  1. tag_cliente > 0 - seleciona todas as pessoas com a característica informada (valor 'S');
  2. cliente_docfat > 0 - seleciona uma pessoa específica;
  3. caso contrário, usa PESSOA_GERAL_FATCONFIG da configuração do módulo.

Se nenhum cliente for encontrado, a execução é interrompida com a exceção "Não há clientes para inclusão.".

Inclusão de itens

A unit P39_TDD_FAT_DOCUMENTO_FATURA_ITENS resolve os itens em três caminhos:

Ordem Condição Comportamento
1 Array item.itens preenchido Inclui exatamente os itens informados no JSON
2 item.tag_prodcomum > 0 Busca produtos pela tag e inclui os detalhamentos encontrados
3 Nenhum dos anteriores Registra assert de falha "Itens Inválidos - Itens não existentes!"

Itens com variação, cor ou acabamento são incluídos através do método Frame.IncluiDetalhamentoItem. Itens sem detalhamento são lançados diretamente no CDSItem (quantidade de chapas e valor unitário bruto).

info Hierarquia de valores por item: o valor do próprio item prevalece; se não informado, usa-se o valor do bloco item; se ainda assim for zero, o valor é sorteado a partir da configuração do módulo. A mesma lógica vale para a quantidade.

Descontos, tabela de preço e prazo

  • A tabela de preço é localizada pela descrição primeiro e, se não encontrada, pelo código — ambas em memória, via FindKey no CDSTabela;
  • A condição de pagamento tem o mesmo tratamento, com fallback de descrição para código;
  • O prazo, quando a condição não bloqueia, pode ser informado manualmente no formato "7/14/21", gerando um registro por prazo em CDSPrazos;
  • O desconto principal aceita múltiplos percentuais separados por vírgula ("10.5, 5.3, 3.1"), e é ignorado quando a tabela de preço bloqueia desconto manual ou não permite desconto — nesse caso o motivo é registrado no log.

Transação de faturamento

A resolução da transação segue a ordem: valor do JSON → PEDIDO_VENDA_FATCONFIG (se maior que zero) → parâmetro do sistema TransacaoVenda lido da seção de parâmetros. Observação: quando o JSON informa transacao_docfat = 0, o valor não é substituído — a variável permanece zero.

arrow_downward Contexto e validação do caso de teste

A rotina SetCasoTeste(pCasoTeste) é executada a cada iteração de Teste_Executar e extrai três blocos do JSON: 

FJSONDOC      := GetObjectJson(pCasoTeste, 'documento');
FJSONITEMCONF := GetObjectJson(pCasoTeste, 'item');
FJSONITENS    := GetArrayJsonOrEmpty(FJSONITEMCONF, 'itens');

Em seguida, o caso é validado por ValidarCasoTeste, que acumula as pendências em FMsgCasoTesteInvalido e define a flag FCasoTesteInvalido. Havendo pendência, uma mensagem interna é enviada ao usuário e o documento não é incluído — mas a execução da suíte continua.

O bloco parametros, se presente, é aplicado por _AjustarParametros, que fecha e reabre o formulário de pedido de venda (ver documentação de Parâmetro).

info A flag ScriptDeTestesEmExecucao é ligada durante a inclusão de itens e desligada no TearDown. Ela existe para que a rotina que dispara o processamento não seja reentrada (executar teste dentro do teste).

arrow_downward Comparação do resultado esperado

A comparação do documento gerado contra o RESULTADO_ESPERADO_CT é orquestrada por P39_TDD_FAT_VALIDAR_RESULTADO, que usa os DataSets registrados pela unit principal:

  1. Cronometro_Iniciar zera os contadores de assert e marca o instante inicial;
  2. Para cada item da seção valor, a rotina CompararValor percorre todos os DataSets registrados, localizando pelo campo informado e executando o assert correspondente;
  3. Campos ftString só aceitam a operação Igual — o uso de Maior / Menor gera assert de falha;
  4. Campos não existentes em determinado DataSet são simplesmente ignorados (Continue), o que permite descrever o mesmo campo em DataSets distintos;
  5. FinalizarComparacao registra no log o resultado da comparação e o resumo dos asserts.

Erros na inclusão de itens não interrompem a execução: são registrados via AssertsFalhou com a mensagem da exceção, e o CDSItem tem o registro cancelado antes de seguir para o próximo item.

arrow_forward Instalação e configurações

Necessário publicar na Tek-Store as units P39_TDD_FAT_DOCUMENTO_FATURA, P39_TDD_FAT_DOCUMENTO_FATURA_ITENS, P39_TDD_DOCUMENTO_FATURA_SQL, P39_TDD_FAT_DOCUMENTO_FATURA_JSON, P39_TDD_FAT_PEDIDO_VENDA e P39_TDD_FAT_VALIDAR_RESULTADO.

A execução deve ser feita em uma instância do ERP com o usuário cliente TekSystem (código 1000), interativamente, e não pelo servidor.

Cadastros e dados necessários

  • Cadastro de pedido de venda publicado e com os componentes estes: FCadPedidoVenda, DMCadPedidoVenda, FRGradeamento, grdItem, BotaoIncluir e BotaoGravar;
  • DataSets CDSCadastro, CDSItem, CDSFiscal, CDSPedido, CDSCondicaoTabela, CDSCondicaoDetalhe, CDSDescontoPrincipal, CDSItemDesconto, CDSTabela e CDSPrazos no data module do cadastro;
  • Módulo FATURAMENTO e área PEDIDO DE VENDA registrados no banco dedicado, com ao menos um caso de teste ativo (ATIVO_CT = 'S');
  • Registro em FATURAMENTO_CONFIGURACAO - define cliente padrão, transação e regras de sorteio de quantidade e valor dos itens;
  • Clientes - ao menos um com a característica informada em tag_cliente, ou o cliente em cliente_docfat, ou o cliente geral da configuração;
  • Itens, cores e acabamentos ativos, quando o caso usa o array item.itens.

arrow_forward Observações importantes

  • Teste com efeito real no banco. Diferente dos demais casos, este cria documentos de venda efetivos. Execute sempre em base de testes.
  • Rastreabilidade. Todo documento gerado recebe a observação "Documento gerado automaticamente via rotina de testes automatizados" acompanhada da descrição do caso de teste, o que permite identificar e limpar os registros gerados.
  • Massa de teste aleatória. Sem valor e quantidade fixos, os itens usam Random. Isso torna a suíte não determinística - asserts de igualdade exata em campos derivados ficam instáveis. Prefira operadores Maior / Menor nesses campos, ou configure valores fixos em FATURAMENTO_CONFIGURACAO.
  • Janela do ERP visível. O formulário é aberto com FormCadastro.Show e permanece visível durante a execução. Qualquer caixa de mensagem de erro do ERP interrompe o fluxo.
  • Falhas não interrompem a suíte. Erros na inclusão de um item e casos de teste inválidos são registrados (assert de falha ou mensagem interna) sem abortar os demais casos. Consequentemente, o log é a evidência do que de fato aconteceu: o status SUCESSO gravado no histórico pode coexistir com asserts de falha.
  • Configuração não carregada. Se FATURAMENTO_CONFIGURACAO estiver vazia, a unit envia mensagem interna "Configuração Não Carregada." e não gera documento, sem interromper a suíte.
  • Validação de asserts em evolução. A rotina CompararResultadoEsperado ainda contém chamadas de depuração (ShowMessage e MostrarCDS), e a comparação da seção tempo está desativada. A comparação da seção erro depende de correção do acesso à subseção JSON. Trate o resultado das asserts com ressalva até a conclusão desses ajustes.
  • Nomenclatura de componente. As constantes FCadastro, FDM, FItemMenu (fixado em 'Emisso1') e os nomes dos DataSets precisam existir exatamente como declarados. Qualquer renomeação no cadastro do ERP exige atualização destas constantes.
  • Cobertura de itens por tag. Quando o caso usa tag_prodcomum, a SQL BuscaDadosProdutos filtra apenas itens, variações, cores e acabamentos com STATUS = 0 e VALOR_ITEMTAG = 'S' - itens inativos simplesmente não entram no documento, sem gerar erro.
