arrow_downward Definições

O caso de teste é a unidade de negócio que descreve o que deve ser testado e com quais dados. Ele vive na tabela CASO_TESTE do banco dedicado de testes e é identificado pela tripla Módulo + Área + Descrição.

fisicamente, um caso de teste é composto por quatro blobs JSON:

  • CASO_TESTE_CT - os dados de entrada do teste (o que será executado);
  • CAMPOS_DISPONIVEIS_CT - a relação de campos que o caso pode utilizar (uso opcional);
  • RESULTADO_ESPERADO_CT - as asserts a serem comparadas ao final;
  • parametros (dentro do JSON do caso) - os parâmetros do sistema a aplicar antes da execução.

Essa separação é o que torna a suíte data-driven: o mesmo código de teste (unit de caso de teste) atende qualquer número de cenários, bastando cadastrar novos registros no banco.

O Runner identifica o caso de teste pela descrição exata (comparação sem diferenciar maiúsculas de minúsculas). Renomear a descrição de um caso de teste ativo quebra a unit que o executa.

Os casos de teste são identificados por descrição e não por código na unit de teste. A unit passa 'FATURAMENTO', 'PEDIDO DE VENDA' e 'PEDIDO COM DESCONTO PERCENTUAL' ao Runner, que faz a conversão para os códigos internos de módulo e área usando o cache.

    Módulo Área Caso de Teste Unit com o JSON de entrada Resultado esperado

    O conteúdo dos JSONs fica em units separadas (nomeadas P39_TDD_JSON_*). Isso é intencional: o dado de teste é versionado como código, enquanto o registro no banco é gerado a partir dele.

  • arrow_downwardDataSets em Memória

    O carregamento feito por P39_TDD_CASOS_DE_TESTE preenche dois DataSets, indexados pelo código do caso de teste:

    DataSet Campos
    CDSCasosTestes ID, MODULO, AREA, DESCRICAO, CASOTESTE (blob), EXECUTADO, COMPARADO
    CDSResultadoEsperado ID, RESULTADO_ESPERADO (blob)

    Os campos EXECUTADO e COMPARADO nacem como 'N' e são usados pela unit de teste para marcar o andamento da suíte (EXECUTADO passa a 'S' ao final de cada caso).

    A consulta base (montada em SQLCasosTestes) filtra somente casos ativos: 

    SELECT AUTOINC_CT,
       DESCRICAO_CASO_TESTE_CT,
       CASO_TESTE_CT,
       CAMPOS_DISPONIVEIS_CT,
       RESULTADO_ESPERADO_CT
FROM CASO_TESTE
where ATIVO_CT = 'S'
  and MODULO_CT = :codigoModulo
  and AREA_CT   = :codigoArea

arrow_forward Instruções de uso

arrow_downward Fluxo geral de uso

Para cadastrar um novo caso de teste, o fluxo é:

  1. Criar a unit com o JSON de entrada do caso, nomeada P39_TDD_JSON_<ASSUNTO>, e publicá-la na Tek-Store;
  2. Se o caso tiver asserts, criar (ou reaproveitar) a unit de resultado esperado;
  3. Adicionar uma linha RegistrarCasoTeste('MÓDULO', 'ÁREA', 'DESCRIÇÃO', 'UNIT_JSON', 'CAMPOS', 'RESULTADO') no corpo de RegistrosCasosTestes;
  4. Executar P39_TDD_SINCRONIZAR_CASOS_TESTE_REGISTRADOS - módulo e área são criados automaticamente se ainda não existirem;
  5. Referenciar o caso pela descrição na unit de teste, ao chamar o {P39_TDD_RUNNER.}Run.

info A sincronização é idempotente: rodar novamente sem alterações não gera diferenças no banco. Se o registro já existir, é exibida uma confirmação antes do UPDATE.

arrow_downward Cadastro e Sincronização

A rotina RegistrarCasoTeste executa, nesta ordem:

  1. Carrega o conteúdo das units JSON informadas (usando CodificacaoUnit). Unit vazia é gravada como {};
  2. Resolve o módulo por descrição; se não existir, cria (RegistroFallbackModulo);
  3. Resolve a área por descrição dentro do módulo; se não existir, cria (RegistroFallbackArea);
  4. Consulta se já existe caso de teste com a mesma descrição + módulo + área;
  5. Se não existir, faz INSERT; se existir, pergunta ao usuário e então faz UPDATE.

warning Todas as inserções e atualizações usam comandos parametrizados (TDDCommandODBCP). Nunca use QuotedStr ao gravar os blobs JSON: aspas literais corrompem o JSON armazenado no banco.

O AUTOINC_CT não é informado no INSERT: o autoincremento é responsabilidade de trigger no banco dedicado.

arrow_downward Estrutura do JSON de entrada

O JSON do caso (CASO_TESTE_CT) é dividido em três blocos de alto nível:

{
  "documento": {
    "cliente_docfat": 1125,
    "descricao_tabela_preco": "TABELA DE PREÇOS FOB 2023",
    "percdesc_docdescprinc": "10.5, 5.3, 3.1",
    "transacao_docfat": 0
  },
  "item": {
    "tag_prodcomum": 0,
    "quantidade": 0,
    "valor": 0,
    "itens": [
      { "item": 2, "variacao": 0, "cor": 23, "acabamento": 0,
        "quantidade": 2, "valor": 355.55, "desconto": 1.1 }
    ]
  },
  "parametros": {
    "ConsideraDiasParaEntregaDupFrete": true,
    "OrdemImpressaoItemNF": 0
  }
}
Bloco Conteúdo
documento Dados do cabeçalho do documento a ser gerado
item Configuração e relação de itens do documento
parametros Parâmetros do sistema aplicados antes da execução (ver documentação de Parâmetro)

info As chaves do JSON são os nomes dos campos do ERP, em minúsculas (ex.: cliente_docfat → CLIENTE_DOCFAT). Os valores são lidos de forma tipada: inteiros, moeda, data e lógico aceitam o valor padrão quando a tag não existe.

arrow_downward Resultado Esperado (asserts)

O blob RESULTADO_ESPERADO_CT descreve o que deve ser verdadeiro ao final do caso:

{
  "erro": {
    "quantidade": 0,
    "operacao": "Igual"
  },
  "valor": [
    {
      "campo": "VALOR_BRUTO_DOCFAT",
      "operacao": "Igual, Maior, Menor",
      "tipo_campo": "ftCurrency",
      "resultado": 1.0
    }
  ],
  "tempo": {
    "tempo_total": 10000,
    "tipo_registo": "data, hora, minuto, segundo, milissegundo"
  }
}
Seção Chave Descrição
erro quantidade, operacao Quantidade de erros reais gerados durante a execução e a operação de comparação (Igual, Maior, Menor)
valor campo, operacao, resultado, tipo_campo Lista de verificações campo a campo nos DataSets registrados
tempo tempo_total, tipo_registo Limite de tempo da execução do caso

Tipos de campo suportados na comparação: ftString (somente Igual), ftInteger, ftCurrency, ftDateTime e ftBoolean.

arrow_downward Execução e carga individual

Na execução da suíte, o STARTED carrega todos os casos ativos do módulo/área e seleciona o pedido. Já a unit P39_TDD_CARREGAR_CASO_TESTE permite carregar um caso específico, útil para depuração pontual: 

{P39_TDD_CARREGAR_CASO_TESTE.}CarregarCasoTeste(
    'FATURAMENTO',
    'PEDIDO DE VENDA',
    'PEDIDO COM DESCONTO PERCENTUAL',
    CDSCasoTeste
);

O DataSet é criado pelo chamador — a unit apenas o popula. Caso o caso não exista ou esteja inativo, a exceção "Caso de teste não encontrado ou inativo." é lançada.

info Nesta routine o fallback está desligado (RegistroFallbackModulo(..., false)): se o módulo ou a área não existirem, o erro é "Recurso não encontrado" — nenhum cadastro é criado.

arrow_forward Instalação e configurações

Necessário publicar na Tek-Store as units de codificação quealke-load do caso de teste (P39_TDD_SINCRONIZAR_CASOS_TESTE_REGISTRADOS, P39_TDD_REGISTRAR_CASO_TESTE, P39_TDD_CARREGAR_CASO_TESTE) e as units de dados P39_TDD_JSON_*.

O acesso ao banco dedicado é feito exclusivamente pelos métodos da unit P39_TDD_ODBC, que usam a conexão TESTE_AUTOMATIZADO_32B. Não declarar string de conexão local nas units de caso de teste.

Cadastros necessários

  • Módulo - registrado automaticamente pelo fallback na primeira sincronização, com a descrição informada no código (ex.: FATURAMENTO, FINANCEIRO);
  • Área - registrada automaticamente dentro do módulo, com a descrição informada (ex.: PEDIDO DE VENDA, BORDERO);
  • Registro único de configuração do módulo - FATURAMENTO_CONFIGURACAO ou FINANCEIRO_CONFIGURACAO, carregado automaticamente conforme o módulo do caso de teste;
  • Histórico de execução - as tabelas HISTORICO_EXECUCAO, METRICAS_TICK_DIFF e METRICAS_ASSERTS (ver documentação do Runner).

warning FATURAMENTO_CONFIGURACAO e FINANCEIRO_CONFIGURACAO não possuem chave primária de propósito: armazenam um único registro de configuração global por módulo. Inserir mais de um registro faz o CDSConfiguracao receber a última linha lida, e a unit passa a se comportar de forma imprevisível.

Reprocessamento de um caso existente

Ao sincronizar, casos já cadastrados exigem confirmação do usuário antes do UPDATE. A pergunta apresentada é: 

Registro para o caso de teste: <DESCRIÇÃO> já existe!
A operação de sincronização será realizada via update. Confirmar esta operação?

arrow_forward Observações importantes

  • Descrição é chave de negócio. Não existem dois casos de teste com a mesma descrição dentro do mesmo módulo/área. Alterar a descrição exige alterar a unit que a referencia.
  • Casos inativos não são removidos. Ao desativar um caso (ATIVO_CT = 'N'), ele deixa de ser carregado pelo Runner, mas continua no banco e no histórico de execuções anteriores.
  • JSON sem aspas literais. Gravações dos blobs devem usar parâmetros (TDDCommandODBCP) e nunca QuotedStr, sob pena de corromper o JSON e fazer o caso falhar na leitura.
  • CAMPOS_DISPONIVEIS_CT é opcional. Os casos cadastrados até hoje não utilizam esse blob; ele existe como contrato de quais campos o caso pode manipular.
  • Comparação de asserts ainda parcial. No fluxo atual, a comparação do resultado esperado é orquestrada por P39_TDD_FAT_VALIDAR_RESULTADO, que está em evolução: a seção tempo ainda não é efetivamente comparada e a comparação da seção erro depende de correção do acesso à subseção JSON. Trate divergências de assert com ressalva até a conclusão desses ajustes.
  • Volumes de teste. Por padrão, o módulo de Faturamento carrega todos os casos ativos da área. Ao acrescentar muitos casos, considere o impacto sobre o tempo total da execução — o Runner mede e grava esse tempo em METRICAS_TICK_DIFF.
